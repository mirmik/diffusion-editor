# 3D-реконструкция в Diffusion Editor

## Статус и цель

Это план первого рабочего прототипа интеграции Pixal3D в
`~/project/diffusion-editor` с визуализацией через Termin.

Пользователь должен иметь возможность:

1. Нарисовать или собрать изображение из обычных слоёв редактора.
2. Создать над ними объект `3D Reconstruction`.
3. Получить 3D-модель из композита нижележащих слоёв.
4. Нарисовать маску уточнения непосредственно поверх исходного изображения.
5. Запустить masked refinement выбранной области.
6. Сравнивать базовую и уточнённые версии модели и экспортировать GLB.

Первая версия предназначена для исследования пайплайна, а не для построения
окончательного универсального 3D-редактора. В интерфейсе должны быть видны
стадии, параметры, времена выполнения, промежуточные результаты и владение
GPU-памятью.

## Основная пользовательская модель

### Реконструкция как специальный объект документа

`3D Reconstruction` отображается в дереве слоёв, но не участвует в обычном
alpha-композитинге. У него отдельная иконка куба и отдельное контекстное
представление.

Пример:

```text
▣ Character reconstruction
──────────────────────────
  Hair details
  Character
  Background
```

Источником реконструкции является композит всех видимых слоёв **под** объектом
`3D Reconstruction`. Сам объект и всё расположенное над ним в источник не
входят. Такая граница делает зависимость явной и не создаёт рекурсию.

Создавать объект предлагается через:

- кнопку с кубом на toolbar;
- `Layer -> New 3D Reconstruction`;
- в дальнейшем — контекстное меню дерева слоёв.

После создания объект автоматически выбирается, открывается его контекстная
панель, а центральная рабочая область переходит в режим реконструкции.

### Рабочая область

Для выбранного реконструкционного объекта центральная область показывает:

- слева — снимок исходного композита и overlay маски;
- справа — 3D viewport Termin;
- разделитель с изменяемой долей;
- возможность временно развернуть любую половину на всю область;
- переключатель версии модели `Base / Refined N`.

Обычный Canvas не следует заменять собственной реализацией. Нужны существующие
zoom/pan, отображение композита, mask brush и преобразование координат
Canvas -> image space. 3D viewport является отдельной native-проекцией Termin.

### Базовый сценарий

1. Пользователь создаёт изображение в существующем редакторе.
2. Нажимает кнопку `Create 3D Reconstruction`.
3. В дереве появляется реконструкционный объект.
4. Панель показывает превью источника и кнопку `Generate`.
5. При `Generate` фиксируется неизменяемый снимок текущего композита под
   объектом и параметры запуска.
6. Pixal3D-worker строит модель в фоне.
7. Готовый GLB загружается через нативный cgltf-бэкенд Termin и появляется в
   viewport.
8. Пользователь экспортирует GLB либо переходит к уточнению.

### Masked refinement

1. Пользователь выбирает `Refine mask`.
2. На левой половине рисует маску в координатах исходного снимка.
3. Панель показывает bounding box маски и эффективный crop.
4. Пользователь задаёт параметры и нажимает `Refine selected region`.
5. Worker использует базовый latent и маску, выполняет уже проверенный
   masked-denoising/refinement и декодирует новую модель.
6. В viewport становится доступно переключение `Base / Refined N`.
7. Базовый результат не перезаписывается.

В первой версии маска одна на реконструкционный объект. Историю нескольких
масок и их отдельное редактирование можно добавить после проверки основного
цикла.

## Изменение исходного изображения

Генерация никогда не перезапускается автоматически.

При изменении слоёв, входящих в исходный композит, реконструкционный объект
получает состояние `source changed`. В дереве и панели появляется индикатор,
но использованный снимок, тензоры и модели остаются неизменными.

Доступные действия:

- `Show captured source`;
- `Compare with current composite`;
- `Update source snapshot`;
- `Regenerate from source`.

`Update source snapshot` должно явно предупреждать, какие производные
артефакты станут устаревшими. До подтверждения ничего не удаляется.

Для первого прототипа допустимо считать реконструкцию устаревшей при любом
изменении дерева или пикселей ниже неё. Точную региональную инвалидацию можно
добавить позднее.

## Доменная модель

Не следует помещать 3D-тензоры и GLB внутрь существующих растровых слоёв.
Нужен специальный тип узла или связанный с узлом ресурс, например:

```text
ReconstructionNode
├── stable_id
├── name
├── source_boundary
├── captured_source
├── source_revision
├── refinement_mask
├── settings
├── runs[]
└── active_run_id

ReconstructionRun
├── run_id
├── parent_run_id
├── kind: base | masked_refine
├── status
├── parameters
├── timings
├── artifact_manifest
├── preview_metadata
└── error
```

Узел должен изменяться через типизированные команды `DocumentService`, как и
остальной документ. Результаты worker-а сначала преобразуются mapper-слоем в
команды приложения; worker и engine не должны мутировать документ напрямую.

Нужно определить явно:

- семантику reorder реконструкционного объекта;
- инвалидацию при изменении нижележащих слоёв;
- удаление объекта без немедленного уничтожения внешних файлов до успешного
  commit операции;
- сохранение stable IDs и активной версии через undo/redo.

## Снимок композита

На момент запуска создаётся immutable RGBA-снимок композита ниже границы
реконструкционного узла. В manifest записываются:

- размер изображения;
- цветовое пространство;
- alpha policy и цвет фона, использованный препроцессором;
- revision/hash композита;
- преобразование исходного изображения в модельный input;
- crop, padding и resize;
- версия препроцессора.

Worker всегда получает снимок, а не живой Canvas. Это гарантирует, что
редактирование документа во время долгого запуска не изменит его вход.

## Контекстная панель

Панель появляется только при выборе `3D Reconstruction` и содержит несколько
сворачиваемых групп.

### Source

- состояние `current / changed`;
- размер и alpha/background policy;
- `Capture/Update source`;
- `Show captured source`.

### Generate

- seed;
- input resolution;
- основные параметры coarse/shape generation;
- `Generate`;
- `Cancel`.

### Refine

- режим рисования/стирания маски;
- размер, hardness и flow кисти;
- отображение маски и crop;
- strength/start timestep;
- количество denoising steps;
- seed/noise policy;
- `Refine selected region`;
- `Clear mask`.

### Pipeline

- список стадий и их статусы;
- время стадии;
- CPU RAM и CUDA VRAM, если доступны;
- просмотр промежуточного результата;
- `Run from here` — не в первом вертикальном срезе;
- `Release inactive models`.

### Result

- выбор run/version;
- видимость текстуры, wireframe и диагностических overlay;
- `Export GLB`;
- позднее — remesh/decimation и перенос текстуры.

## Pixal3D engine и worker

Pixal3D не должен импортироваться в UI-процесс. Нужен отдельный процесс по
паттерну существующих model workers Diffusion Editor.

Разделение ответственности:

```text
UI / Coordinator
    typed intents + immutable snapshots
             |
ReconstructionEngine
    lifecycle, очередь одного запуска, poll/cancel
             |
Pixal3DProcessClient
    компактный IPC-протокол
             |
Pixal3D worker process
    модели, CUDA, тензоры, стадии пайплайна
             |
Artifact store
    manifests, tensors, meshes, previews
```

Через IPC передаются команды, прогресс, ошибки и небольшие метаданные. Большие
тензоры, изображения и меши передаются по явным путям к артефактам. Нельзя
сериализовать многомегабайтные тензоры в JSON или копировать их через stdout.

Worker должен поддерживать как минимум:

- `probe`;
- `generate_base`;
- `refine_masked`;
- `cancel`;
- `release_stage_models`;
- `shutdown`.

Протокол должен быть версионирован. Сообщения stdout зарезервированы под
протокол; логи идут по предусмотренному каналу/stderr и проецируются в
диагностику редактора.

## Артефакты и воспроизводимость

Предлагаемый каталог одного запуска:

```text
reconstruction-runs/<node-id>/<run-id>/
├── manifest.json
├── source.png
├── mask.png                  # только для refine
├── preprocessed.png
├── conditioning.safetensors  # если сохраняется данной стадией
├── shape-latent.safetensors
├── refined-latent.safetensors
├── occupancy.*
├── mesh.glb
└── previews/
```

Точный набор файлов зависит от доступных точек входа Pixal3D. Manifest является
источником истины и содержит:

- schema version;
- тип запуска и parent run;
- параметры всех выполненных стадий;
- seed;
- версии кода и checkpoints;
- входные и выходные shapes/dtypes;
- пути, размеры и hashes артефактов;
- timings;
- завершённость каждой стадии.

Запись каждой стадии транзакционная: временный файл переименовывается и
регистрируется в manifest только после успешной записи. Прерванный запуск не
должен выглядеть завершённым.

Для первой версии `.pt` допустим для уже существующих экспериментальных точек
входа. Для долговременного и проверяемого обмена тензорами предпочтителен
`safetensors`, когда структура данных это позволяет.

## Визуализация

### Готовый mesh

Итоговые и промежуточные GLB загружаются нативным cgltf-бэкендом Termin.
Viewport должен уметь хотя бы:

- orbit/pan/zoom;
- fit model;
- lit и wireframe режимы;
- выбор base/refined результата;
- отображение текстурированного и нетекстурированного mesh;
- простую статистику vertices/triangles/materials.

### Occupancy, sparse structure и latent diagnostics

Не следует преобразовывать каждый промежуточный тензор в сокращённый
треугольный GLB. Это искажает исследуемые данные и добавляет лишние расходы.
Для точек/вокселей нужен прямой диагностический drawable Termin с ограничением
числа отображаемых элементов и управляемым sampling. Это отдельный этап после
базового вертикального среза.

## Управление памятью

Интерфейс должен отражать реальный staged execution:

- model components загружаются лениво;
- worker явно выгружает больше не нужные компоненты;
- CPU-тензоры можно сохранять на диск и освобождать;
- перед переходом к следующей тяжёлой стадии выполняется синхронизация и
  контролируемая очистка CUDA cache;
- UI получает события `stage_started`, `stage_progress`, `stage_completed`,
  `artifact_published`, `memory_snapshot`, `failed`, `cancelled`;
- падение worker-а не должно падать вместе с редактором.

Кнопка `Cancel` обязана быть честной: если конкретный CUDA-вызов нельзя
прервать, UI сообщает `cancelling` и завершает операцию на ближайшей безопасной
границе.

## История и сохранение проекта

Встроить гигантские тензоры непосредственно в snapshot-based undo нельзя.
История хранит небольшие immutable manifests/ссылки на content-addressed или
run-scoped артефакты. Физическое удаление файлов выполняется сборщиком мусора,
когда на run больше не ссылаются документ, undo/redo и активный worker.

В первом прототипе допустимо:

- хранить артефакты во внешнем project cache;
- сохранять в документе относительные ссылки и hashes;
- при открытии показывать понятное состояние `artifact missing`;
- не упаковывать тяжёлые тензоры в основной архив проекта.

## Этапы реализации

### Этап 0. Зафиксировать контракты

- Определить `ReconstructionNode`, `ReconstructionRun` и команды документа.
- Определить семантику композита ниже узла.
- Описать manifest schema и IPC protocol.
- Сделать fake worker для UI и lifecycle-тестов.

Критерий готовности: headless-тест создаёт узел, фиксирует source snapshot,
применяет fake result через mapper и восстанавливает состояние через undo/redo.

### Этап 1. Первый вертикальный срез

- Команда и toolbar button создания реконструкционного объекта.
- Отображение объекта в дереве с отдельной иконкой.
- Контекстная панель с `Generate/Cancel/Export`.
- Снимок композита нижележащих слоёв.
- Отдельный Pixal3D worker с базовой генерацией.
- Artifact manifest и сохранение GLB.
- 3D viewport с загрузкой через cgltf.
- Прогресс, ошибка и безопасное завершение worker-а.

Критерий готовности: пользователь рисует/открывает изображение, создаёт
реконструкцию, нажимает `Generate`, видит модель в Termin и экспортирует тот же
GLB. UI остаётся отзывчивым, а повторное открытие результата не требует
повторной генерации.

### Этап 2. Masked refinement

- Mask overlay и существующие brush controls в image space.
- Сохранение маски и crop transform.
- Загрузка базового latent из артефакта.
- Вызов проверенного masked refinement.
- Parent/child runs и переключение `Base / Refined`.
- Временные и VRAM diagnostics.

Критерий готовности: маска головы создаёт отдельный уточнённый run; базовый run
остаётся доступен; после перезапуска редактора обе версии открываются из
manifest и визуально переключаются.

### Этап 3. Прозрачные стадии

- Pipeline timeline.
- Сохранение и повторное использование промежуточных тензоров.
- `Run from here` и инвалидация только зависимых стадий.
- Просмотр occupancy/sparse данных напрямую в Termin.
- Сравнение параметров и времени runs.

Критерий готовности: можно остановиться после выбранной стадии, закрыть worker,
затем продолжить с сохранённого совместимого артефакта.

### Этап 4. Геометрическая обработка

- decimation/remesh как отдельная производная операция;
- сравнение геометрии и статистики;
- восстановление/перенос текстур;
- контроль self-intersections и деградации силуэта.

Эта стадия не должна блокировать базовую генерацию и masked refinement.

## Тестовая стратегия

### Домен и приложение

- source boundary исключает сам реконструкционный узел и слои выше;
- изменения ниже выставляют `source changed`, изменения выше — нет;
- запуск использует immutable snapshot;
- mapper публикует результат только для существующего node/run;
- поздний результат отменённого запуска не применяется;
- undo/redo сохраняет ссылки на runs и активную версию;
- удаление узла не удаляет артефакт, пока он нужен истории.

### Worker и IPC

- fake backend без моделей для CI;
- protocol version mismatch;
- cancel/shutdown;
- worker crash и восстановление UI;
- частично записанный артефакт не публикуется;
- повторное чтение завершённого manifest.

### Native UI

- стабильные IDs новых контролов;
- создание/выбор реконструкционного узла;
- появление контекстной панели;
- переключение Canvas/3D split;
- busy/failed/cancelled states;
- smoke с настоящим GLB через cgltf.

### Реальный smoke

1. Простая Pixal3D-модель с текстурой.
2. Большая человеческая фигура.
3. Уточнение головы существующим экспериментальным сценарием.
4. Визуальное сравнение base/refined и проверка повторной загрузки.

## Что не включать в первый вертикальный срез

- автоматический remesh;
- редактирование mesh кистью;
- сшивание двух независимых поверхностей;
- multiview conditioning;
- полноценный 3D scene graph;
- упаковку всех тензоров внутрь файла документа;
- автоматическую регенерацию после каждого изменения исходных слоёв;
- одновременное выполнение нескольких тяжёлых Pixal3D jobs.

## Рекомендуемые технические границы

- UI-проекция остаётся тонкой и получает immutable snapshots.
- Координатор владеет intents и presentation state.
- `ReconstructionEngine` владеет lifecycle одного задания, но не CUDA-моделью.
- Worker владеет Pixal3D, CUDA и промежуточными in-memory тензорами.
- Artifact store владеет атомарной публикацией и проверкой manifest.
- Termin viewport владеет только ресурсами визуализации, не исходными ML
  тензорами.
- Все изменения документа проходят через `DocumentService`.
- Ошибки не проглатываются: они логируются и отображаются в состоянии run.

## Первый практический шаг

Начать следует с fake worker и настоящего UI/документного пути, а затем заменить
единственную команду `generate_base` на вызов Pixal3D. Это отделит проблемы
интеграции Termin и модели документа от проблем CUDA-окружения.

Минимальная демонстрация первой итерации:

```text
нарисовать/открыть изображение
    -> Create 3D Reconstruction
    -> Generate (fake или заранее подготовленный GLB)
    -> показать GLB в native viewport
    -> сохранить и повторно открыть проект
```

После этого подключить настоящий базовый inference, и только затем masked
refinement. Такой порядок сохраняет архитектуру проверяемой и быстро даёт
видимый результат.
